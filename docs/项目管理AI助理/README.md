## 1. 本目录的用途

本目录是项目助理、交付项目 PMO 及其与汇报助理协同关系的当前需求基线。后续开发应先查阅本索引和对应页面文档，避免只依据现存组件、隐藏菜单或旧方案继续开发。

资料优先级如下：

1. 本索引中的“已确认决策”。
2. 本目录中状态为“已确认”的页面文档。
3. 本目录中状态为“建议方案”的页面文档。
4. 会议纪要与历史改造方案。
5. 当前代码。当前代码只能说明已经做过什么，不能自动代表最终需求。

## 3. 已确认决策

- 数字员工以左侧头像为入口，进入后默认打开该数字员工的“对话”页面。
- 数字员工的相关功能以顶部菜单呈现。
- 梳理当前能力时忽略隐藏菜单；隐藏组件可以在后续页面中复用，但不因其存在而自动恢复菜单。
- 系统是界面流程 Demo，重点是把管理逻辑、页面状态和跨页面闭环表达清楚，不要求真实文档解析或生产级后端。
- 采用逐页确认、逐页开发的方式，避免一次性改完后整体返工。
- 交付项目 PMO 原“项目模板配置”正式命名为“制度与模板”。
- 数字员工实例名称改为“交付项目 PMO”；底层保留通用“项目 PMO”能力，通过部门模板、制度和术语配置复用。
- 单独设置“项目立项”菜单，承载项目资料、AI 解析、宪章确认和基线生成；“项目”只承载立项后的执行管理。
- “项目立项”只展示未生效草稿；基线发布后记录移出立项列表并进入“项目”页面。
- “项目立项”默认只做草稿管理；新增或继续草稿后进入独立四步向导，不再与管理列表同屏编辑。
- “制度与模板”默认只做模板、审核建议和制度来源管理；新增模板进入独立四步向导，首步支持上传资料或粘贴管理要求。
- 生成项目基线前必须由管理者确认阶段与目标、范围与成果物、RACI 与资源；阶段目标和 RACI 支持编辑，编辑后需重新确认；立项不设置独立审核步骤。
- 阶段 AI 建议先用 3～4 字短标题区分方案，详细指导随后展示，行动草稿默认折叠。
- 主业务逻辑为：部门负责人上传项目资料或制度资料 → AI 解析制度、合同和模板 → 人工确认项目基线 → 执行者通过周报汇报目标、成果物和阻塞 → AI 识别风险并提出有依据的操作建议 → 管理者确认干预动作。

### 4.3 汇报助理协同改造

汇报助理暂不计入上述 9 个项目管理菜单，但必须承担执行数据入口：

- “本周周报”改成“计划内项目 + 计划外工作”双轨结构。
- 计划内汇报必须可以关联项目 → 阶段 → Objective → KR → Deliverable。
- 阻塞和成果物证据提交后可被项目助理和交付项目 PMO 消费。
- 原“与我相关”拟扩展为“协作任务”，承载明确下达的轻量任务以及待回应协作；该命名和合并范围仍待确认。

## 5. 跨页面业务闭环

```text
Policy Source（公司制度）
        ↓ AI解析 + 人工确认
Project Template（可复用模板）
        ↓ 结合合同/SOW与项目描述
Initiation + Project Charter（项目宪章）
        ↓ 人工批准
Project Baseline（阶段/O/KR/成果物/责任/门禁）
        ↓ 执行
Weekly Report（计划内进展 + 计划外工作 + 阻塞 + 证据）
        ↓
Risk Signal（风险信号与依据）
        ↓ AI建议 + 人工授权
Intervention（提醒、重承诺、调整、升级）
        ↓
后续周报验证干预结果，并沉淀为制度或模板改进建议
```

## 7. 建议开发顺序

1. 制度与模板：先确定标准如何形成。
2. 项目治理：再确定模板、合同如何生成项目宪章和基线。
3. 我的项目：让执行者能看到已确认基线。
4. 汇报助理项目闭环：收集实际进展、成果物和阻塞。
5. 成果物：完善提交、自检、验收和证据回流。
6. 风险与干预：利用前述数据形成管理动作。
7. 今日推进与管理驾驶舱：分别形成执行者和管理者的聚合入口。
8. 两个对话页面：最后统一上下文跳转和动作生成能力。

开发顺序不是确认结果；用户可以在逐页确认时调整。

## 8. 文档维护规则

- 页面开始开发前，将其状态改为“已确认”或“开发中”。
- 页面设计发生变化时，先改文档，再改代码。
- 页面完成后补充实际路由、组件、Mock 数据和已验证交互。
- 新增跨页面规则时，同时更新本索引的闭环图和根目录 `CONTEXT.md`。
- 不能用隐藏组件或旧文档覆盖用户后续确认的新决策。

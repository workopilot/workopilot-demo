# 喔壳 Demo 开发规范

版本：V1.0  
更新日期：2026-11-16  
适用范围：喔壳 Demo 的新增功能、页面设计、交互实现和 Mock 数据开发。

本文件是完整开发规范的统一维护位置。所有 Agent 开始相关开发前，必须先完整阅读本文，并结合根目录 [AGENTS.md](../AGENTS.md) 执行；交付前按第 9 节验收清单核对本次改动。后续规范更新统一修改本文，其他指引通过链接引用。

> 喔壳 Demo 是一个以数字员工为业务入口、使用 Mock 数据演示业务的前端系统。数字员工承载业务办理，应用承载业务配置；对话和业务页面共同完成同一套业务流程。

## 1. 项目定位

本项目用于演示喔壳的产品形态、业务场景和交互流程，帮助使用者理解数字员工如何协助完成工作。

- 以可运行、可操作、可连续演示的业务闭环为交付目标。
- 使用前端 Mock 数据模拟业务记录、配置、接口响应和状态变化。
- 对话可使用预设意图、示例问题和模拟执行过程，不要求连接真实大模型。
- 新增业务不要求实现真实后端、数据库或第三方系统对接。
- 页面以中文为主，使用现有 Ant Design Vue 和 Vben 体系。
- Demo 应呈现完整的业务体验：主要按钮能够操作，操作结果能够查询，状态变化能够解释。

## 2. 核心概念

| 概念 | 定义 | 会议场景示例 |
| --- | --- | --- |
| 数字员工 | 围绕一类业务职责组织的工作入口，包含对话和业务菜单 | 会议助理 |
| 对话 | 数字员工的第一个菜单，用户通过自然语言查询、发起和处理业务 | “帮我预约明天下午的项目评审会” |
| 业务菜单 | 与对话并列，展示和操作日常业务对象或工作结果 | 我的会议、会议纪要 |
| 应用 | 某类业务的配置入口，供业务管理员维护业务设置 | 会议应用 |
| 业务配置 | 影响业务如何运行的资源、规则、模板等设置 | 会议室、预约规则、纪要模板 |
| 业务记录 | 用户办理业务时产生或维护的具体对象 | 一条会议预约、一份会议纪要 |
| 业务用户 | 通过数字员工办理日常工作的使用者 | 预约会议、查看会议的员工 |
| 业务管理员 | 负责维护某个应用业务配置的角色 | 维护会议室及预约规则的管理员 |

数字员工与应用是同一业务的不同入口。两者应复用相应的业务数据和配置，不要求机械地一一对应，也不要为了新增一个数字员工重复实现一套配置。

## 3. 产品信息架构

```text
喔壳 Demo
├── 数字员工                         用户办理业务
│   └── 会议助理
│       ├── 对话                     第一个菜单，默认入口
│       ├── 我的会议                 查询、预约、查看、调整会议
│       └── 会议纪要                 查看、编辑、确认会议纪要
└── 应用                             业务管理员配置业务
    └── 会议应用
        ├── 会议室设置
        ├── 预约规则
        ├── 会议纪要模板
        └── 业务权限与通知规则        按场景需要提供
```

### 3.1 数字员工入口

- 以业务职责命名，例如会议助理、销售助理、汇报助理。
- 进入数字员工后，默认打开“对话”。
- 第一个菜单统一命名为“对话”，不使用“数字员工”“AI 助手”等替代名称。
- 对话旁边放置同级业务菜单，承接当前数字员工职责内的业务。
- 菜单按业务对象或工作结果命名，例如“我的会议”“客户”“商机”“历史报告”。
- 菜单数量以演示需要为准，不强制为每个业务动作增加一个菜单。预约会议可以是“我的会议”中的操作。

### 3.2 应用入口

- 应用集中承载该业务的配置，由业务管理员维护。
- 配置内容包括业务资源、基础资料、规则、模板、权限等，具体范围随业务确定。
- 普通用户在数字员工中使用这些配置产生的能力，不需要进入应用配置才能办理业务。
- 同一个人可以同时是业务用户和业务管理员；两类职责通过入口和页面内容区分。
- 只影响个人的通知偏好、个人展示偏好可以放在个人设置中，不视为全局业务配置。

### 3.3 页面归属判断

判断一个页面应放在哪里，先回答：它是在“办理一笔业务”，还是在“配置业务如何运行”？

| 功能 | 所属入口 | 判断依据 |
| --- | --- | --- |
| 查询明天有哪些会议 | 数字员工：对话／我的会议 | 查询业务记录 |
| 预约、改期、取消一场会议 | 数字员工：对话／我的会议 | 办理具体业务 |
| 编辑某场会议的纪要 | 数字员工：会议纪要／会议详情 | 维护业务成果 |
| 查询当前可预约的会议室 | 数字员工：预约过程 | 使用已配置的业务资源 |
| 新增会议室、调整容量和设备 | 应用：会议室设置 | 维护共享资源 |
| 设置预约提前量和冲突规则 | 应用：预约规则 | 配置业务规则 |
| 配置纪要章节和输出格式 | 应用：会议纪要模板 | 定义可复用模板 |
| 修改个人提醒偏好 | 个人设置 | 只影响当前用户 |

是否使用表格、表单或聊天界面，不决定页面的业务归属。

## 4. 对话与业务页面规范

### 4.1 对话必须能够操作业务

对话的核心是让用户通过自然语言完成职责范围内的业务。至少围绕主要演示场景提供：

1. **明确入口**：展示当前数字员工能做什么，并给出可点击的示例问题。
2. **理解需求**：识别业务意图、提取相关字段。
3. **补充信息**：缺少时间、对象等必要信息时，继续询问或提供选择。
4. **展示预览**：创建、修改、取消等操作展示关键内容；影响较大的操作提供确认步骤。
5. **执行操作**：调用统一的 Mock 业务方法，更新业务状态。
6. **展示结果**：返回结果卡片、记录摘要或详情入口，并支持下一步操作。

例如预约会议：

```text
用户提出预约需求
→ 助理补齐时间、参会人等信息
→ 按会议应用配置查询会议室与预约规则
→ 展示预约信息并确认
→ 创建 Mock 会议记录
→ 返回预约结果与“查看会议”入口
→ 用户在“我的会议”中看到同一条记录
```

不要将业务执行简化为一段固定的“已完成”回复。未识别的输入、缺少信息、时间冲突等情况也应有明确反馈。

### 4.2 业务页面承接持续操作

- 列表用于查询、筛选、查看状态和发起常用操作。
- 详情用于查看完整信息、关联记录和后续动作。
- 表单用于直接创建或编辑业务记录，不强制用户所有操作都通过对话完成。
- 对话结果应能定位到对应记录；业务页面可按需要提供“让助理处理”的入口。
- 页面切换时保持合理的选中状态、筛选条件和返回路径。

### 4.3 同一业务共用同一份状态

- 对话、列表、详情、统计视图读取同一份业务状态。
- 对话中创建会议后，列表和详情应同步显示；列表中改期后，再次对话查询应返回新时间。
- 对话与表单复用创建、更新、取消等业务方法，避免两套逻辑产生不同结果。
- 应用配置应对后续操作生效。例如禁用会议室后不能继续预约，切换纪要模板后新生成的纪要应采用相应结构。
- 修改配置是否影响已有记录，应根据业务明确约定；不要无提示地改写历史记录。

## 5. Mock 数据与接口规范

### 5.1 数据组织

按业务拆分 Mock 数据、接口和类型，避免继续把所有场景堆在一个文件中。

```text
apps/web-antd/src/
├── api/
│   ├── mock-data.ts                 现有公共 Mock 工具
│   ├── mock-data-meeting.ts         会议场景数据
│   └── meeting.ts                   查询、预约、改期、取消等方法
├── types/
│   └── meeting.ts                   会议、会议室、模板等类型
└── views/
    └── <业务模块>/
        ├── components/              业务子组件
        └── modals/                  表单与弹窗
```

目录为新增业务的组织示例，不表示会议模块已经按此完整实现。

### 5.2 数据要求

- 使用虚构名称、演示数据和占位凭据，不写入真实客户隐私或访问密钥。
- 业务记录使用稳定 ID，关联记录通过 ID 关联，状态名称保持一致。
- 覆盖演示流程需要的状态，例如待开始、已结束、已取消，以及无数据、冲突、失败等场景。
- 时间数据以明确的演示基准或当前时间偏移组织，避免“明天的会议”等演示因日期过期失效。
- 默认在内存中维护状态，刷新页面重置；需要持久化的模块应明确保存范围和重置方式。
- 不将业务数据分别硬编码在对话、列表和详情组件中。

### 5.3 接口要求

复用现有 `createMockResponse` 与 `mockDelay`，统一返回：

```ts
{
  code: 0,
  data: result,
  message: 'success',
}
```

- 查询支持演示需要的筛选、分页和关联信息。
- 创建、修改、删除或状态流转必须真实改变 Mock 状态。
- 校验失败时返回或抛出可供页面展示的业务错误，不返回虚假的成功。
- 页面调用统一业务方法，并按模块现有方式同步响应式状态或刷新查询。
- AI 等待、解析、生成等过程可以模拟，但最终结果应与当前业务数据和配置一致。

## 6. 前端实现规范

### 6.1 技术栈与组件

- 使用 Vue 3、TypeScript、Vite、Vben Admin 5、Ant Design Vue。
- Vue 页面使用 `<script setup lang="ts">`，为业务类型、Props、Emits 定义明确类型。
- 显式导入使用的 Ant Design Vue 组件，并使用 PascalCase 标签，例如 `<Button>`、`<Table>`。
- 优先复用项目已有的 Vben 表单、弹窗、表格封装及数字员工工作区、工具栏、应用布局。
- 样式使用 Tailwind 与局部样式，保持页面间的字号、间距、颜色和状态表达一致。
- 图标使用 `@iconify/vue` 或 `@vben/icons` 的 `IconifyIcon`，优先 Lucide，在线按需加载。
- 不恢复全量 `@iconify/json` 数据包、Tailwind 图标插件或 `icon-[...]` 图标语法。
- 不新增 Element Plus、Naive UI、TDesign 模板应用。

### 6.2 路由与菜单

- 普通后台模块遵循 `src/router/routes/modules/` 的路由组织。
- Mate 数字员工和应用页面遵循现有 `src/router/routes/core.ts` 的独立用户端挂载方式，避免误套后台布局。
- 员工注册、菜单定义、路由、默认跳转应保持一致；新增菜单必须有可访问页面。
- 数字员工相关注册和菜单目前集中在 `src/api/mock-data-mate.ts`，新增功能需同步核对。
- 路由页面按需加载；菜单第一项及默认跳转均为“对话”。
- 业务管理员配置入口按角色展示。Demo 可模拟角色切换和访问范围，无需因此实现生产级后台权限系统。

### 6.3 文件边界

- 页面放在对应业务目录，子组件放在 `components/`，弹窗放在 `modals/`。
- 列表、详情、表单、对话结果卡片和复杂状态逻辑按职责拆分，避免一个页面承担全部功能。
- 不为多个入口复制业务数据、配置或整套页面逻辑。
- 不修改 `packages/@core/` 和 `views/_core/`；业务需求优先在应用层实现。
- 不因一次演示需求引入新的后端、国际化体系或大型依赖。

## 7. 新增数字员工的开发流程

1. **确定业务职责**：明确服务谁、处理哪些业务、主要演示场景是什么。
2. **划分入口**：列出“对话 + 业务菜单”和“应用配置”，逐项确认归属。
3. **明确业务对象**：定义记录、状态、关联关系，以及配置如何影响操作。
4. **准备 Mock 数据**：覆盖主流程、边界场景和可重复演示的初始状态。
5. **实现统一业务方法**：先保证查询和状态流转，再由对话、表单和列表复用。
6. **实现页面与菜单**：复用现有布局，完成默认跳转、详情入口和操作反馈。
7. **串联演示流程**：从应用配置出发，完成对话办理、业务查询和后续操作。
8. **验证与说明**：记录已实现能力、模拟范围、重置方式和检查结果。

## 8. 会议场景的最低演示闭环

| 阶段 | 演示动作 | 应观察到的结果 |
| --- | --- | --- |
| 管理员配置 | 在会议应用中设置可用会议室和纪要模板 | 配置能够保存并供业务使用 |
| 用户进入 | 打开会议助理 | 默认显示第一个菜单“对话” |
| 对话预约 | 提出会议需求并补齐信息 | 助理展示可用资源和预约信息 |
| 确认执行 | 确认预约 | 创建真实的 Mock 会议记录 |
| 页面查询 | 打开“我的会议” | 找到刚创建的同一条会议 |
| 后续操作 | 在页面中改期或取消 | 列表、详情和再次对话查询保持一致 |
| 生成成果 | 模拟会议结束并生成纪要 | 纪要采用应用中配置的模板 |
| 异常演示 | 尝试预约冲突时间或不可用会议室 | 展示明确原因和可继续操作的方案 |

上表是开发和验收目标，不表示当前代码已完成全部会议能力。

## 10. 既有实现的适用说明

本规范以当前明确的产品规则为准。现有页面中存在尚未统一的命名和入口，后续按任务范围逐步调整：

- 部分数字员工的首菜单仍叫“数字员工”，应统一为“对话”。
- 会议助理当前只注册了对话菜单，后续按演示范围补充“我的会议”等业务入口。
- 某些员工菜单承载了制度、模板等配置，需按“具体业务办理”和“可复用业务配置”重新判断归属。

本次规范整理不代表这些页面已经完成改造，也不要求为一次局部开发同时重构所有历史模块。
